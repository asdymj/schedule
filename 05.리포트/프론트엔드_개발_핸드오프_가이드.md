## 1. 핸드오프 3대 원칙

| # | 원칙 | 설명 |
|---|------|------|
| 1 | **프로토타입 = 시각적 명세, 정본 아님** | 프로토타입 HTML은 "어떻게 보이는가"의 레퍼런스일 뿐, "어떤 화면/구조/데이터인가"는 화면설계서(#9) SCR-ID가, "어떤 색·폰트·간격인가"는 디자인가이드(#13) 토큰이 정본(Source of Truth)입니다. 셋이 충돌하면 **#9·#13 우선**, 프로토타입은 시각적 의도 파악용으로만 참조합니다. |
| 2 | **인라인 스타일 금지 → 토큰/컴포넌트로 치환** | 프로토타입의 `style="color:#FF8FA3; padding:16px"` 같은 인라인 값을 그대로 복사하지 않습니다. 반드시 디자인가이드 §10 토큰(`text-primary`, `p-4` 등 Tailwind 클래스)으로 매핑하고, 반복되는 시각 패턴은 `components/ui/`의 공용 컴포넌트로 추출합니다. |
| 3 | **서버 컴포넌트 기본, 상호작용만 클라이언트** | Next.js 14 App Router 기준 모든 화면은 **서버 컴포넌트로 시작**하고, 클릭/입력/애니메이션/상태 등 상호작용이 필요한 최소 단위에만 `'use client'`를 선언합니다. 프로토타입의 JS 인터랙션을 통째로 클라이언트화하지 말고, 인터랙션 경계를 분리 설계합니다. |

## 2. 3중 정합 매핑 — 한 줄 요약

```
[프로토타입 HTML]  --(시각 의도 추출)-->  [화면설계서 #9: SCR-ID·구조·API]  --(토큰 매핑)-->  [디자인가이드 #13: 색·폰트·간격·컴포넌트 토큰]
        시각(What it looks like)              구조(What it is / does)              규격(What values to use)
            ↓ 참조만                              ↓ 정본 (구조 정합)                    ↓ 정본 (값 정합)
                              =====>  최종 코드: app/{SCR-ID 라우팅}/ + components/ui/{토큰 기반 컴포넌트}
```

| 계층 | 정본 여부 | 책임 범위 | 코드 반영 위치 |
|------|-----------|-----------|----------------|
| 프로토타입 (시각) | 참조용 | 레이아웃 의도, 시각적 위계, 인터랙션 아이디어 | (코드에 직접 반영 안 함 — 설계 인풋으로만 소비) |
| 화면설계서 #9 (구조) | **정본** | SCR-ID, URL 라우팅, 화면 구성요소, API 연동, 검증/에러 시나리오 | `app/{route}/page.tsx`, `app/api/*` 매핑 |
| 디자인가이드 #13 (토큰) | **정본** | 컬러·타이포·스페이싱·아이콘·컴포넌트 규격, 라이트/다크 토큰 | `tailwind.config.js`, `components/ui/*`, CSS 변수 |

### 2.1 정합 체크 절차 (화면 1개당)

1. **구조 확정**: 프로토타입에서 해당 화면을 찾아 화면설계서 §2 카탈로그에서 일치하는 **SCR-ID**를 확정 (예: 로그인 화면 → `S-COMMON-LOGIN`)
2. **API/상태 확인**: 해당 SCR-ID의 "관련 기능"·"관련 API" 행을 읽고, 프로토타입의 더미 데이터를 실제 데이터 흐름(API 응답 타입)으로 치환할 지점을 표시
3. **토큰 치환**: 프로토타입의 색상 Hex·px 값을 디자인가이드 §3·§4·§10의 토큰명으로 1:1 매핑표 작성 (아래 §3 참조)
4. **컴포넌트 분해**: 반복 시각 패턴을 디자인가이드 §6 컴포넌트 목록과 대조하여 기존 `components/ui/` 컴포넌트 재사용 여부 판단, 신규 시 명명 규칙에 따라 추가
5. **불일치 처리**: 프로토타입에만 있고 #9/#13에 없는 요소는 **임의 반영 금지** → PM에게 보고 후 #9/#13 갱신 또는 폐기 결정

## 3. 인라인 스타일 → Tailwind 토큰 치환 계획

프로토타입에서 흔히 나타나는 인라인 값 패턴과 변환 규칙입니다. (디자인가이드 §10 토큰 네이밍 규칙 기준)

| 프로토타입 패턴 (예시) | 금지 | 치환 대상 | Tailwind/토큰 |
|------------------------|------|-----------|----------------|
| `style="color:#FF8FA3"` | 하드코딩 Hex | `--color-primary` | `text-primary` (CSS 변수 매핑) |
| `style="background:#FFF8F2"` | 하드코딩 Hex | `--color-bg` | `bg-background` |
| `style="padding:16px; margin-top:24px"` | px 직접 입력 | `space-4`, `space-5` | `p-4 mt-6` (4pt 그리드 매핑) |
| `style="border-radius:12px"` | px 직접 입력 | `radius-button` | `rounded-button` (커스텀 radius 토큰) |
| `style="font-size:18px; font-weight:600"` | 임의 폰트 값 | `H2` 타입 토큰 | `text-h2` (커스텀 typography 유틸) |
| `style="box-shadow:0 2px 8px rgba(0,0,0,0.06)"` | 임의 그림자 | `shadow-card` | `shadow-card` |
| `<button style="...">` 반복 | 인라인 버튼 스타일 | `Button` 컴포넌트 | `<Button variant="primary" size="md">` |
| `<div class="card" style="...">` | 커스텀 클래스+인라인 혼용 | `Card` 컴포넌트 | `<Card>` (`components/ui/card.tsx`) |

> 변환 작업은 **컴포넌트 단위**로 진행: 프로토타입 → ① 토큰표 작성 → ② `components/ui/` 컴포넌트 존재 여부 확인 → ③ 신규/재사용 결정 → ④ Tailwind 클래스로 치환. 임의의 매직 넘버(예: `mt-[23px]`)는 디자인가이드 스케일에 가장 가까운 공식 토큰으로 반올림하여 사용합니다.

## 4. Next.js 14 App Router 구조 기준

### 4.1 디렉토리 매핑 (SCR-ID → 라우트)

```
src/frontend/app/
├── (auth)/
│   └── login/page.tsx                    ← S-COMMON-LOGIN
├── onboarding/page.tsx                   ← S-COMMON-ONBOARDING
├── home/page.tsx                         ← S-COMMON-HOME
├── g/[gid]/
│   ├── cal/[view]/page.tsx               ← S-CAL-MONTH/WEEK/DAY/LIST
│   ├── e/[eid]/page.tsx                  ← S-EVENT-DETAIL
│   ├── e/[eid]/decorate/page.tsx         ← S-EVENT-EDITOR (캔버스, 클라이언트 비중 高)
│   ├── members/page.tsx                  ← S-GROUP-MEMBERS
│   └── invite/page.tsx                   ← S-GROUP-INVITE
├── api/                                  ← Route Handlers (M1~M4, API스펙 #7 매핑)
└── ...
```

> 라우팅 세그먼트명은 화면설계서 §3~§10의 URL 패턴(`/g/:gid/cal/month` 등)을 그대로 따릅니다. SCR-ID는 코드 주석/컴포넌트명에 명시하여 추적성을 유지합니다 (예: `// SCR-ID: S-CAL-MONTH`).

### 4.2 서버/클라이언트 경계 판단 기준

| 화면 특성 | 기본 | 'use client' 적용 범위 |
|-----------|------|------------------------|
| 정적 정보 표시 (마이페이지, 알림 설정 목록) | 서버 컴포넌트 | 토글 스위치 등 개별 인터랙션 단위만 분리 |
| 데이터 목록 + 필터/탭 (캘린더 월 뷰, 갤러리) | 서버 컴포넌트(초기 데이터) | 필터 칩, 뷰 전환, 무한 스크롤만 클라이언트 하위 컴포넌트로 |
| 폼 입력 (일정 생성, 그룹 생성, 로그인) | 서버 컴포넌트(레이아웃) | `<form>` 내부 입력·검증·제출 로직만 클라이언트 컴포넌트 |
| 캔버스 에디터 (S-EVENT-EDITOR) | 클라이언트 비중 불가피 | 캔버스 전체를 클라이언트 컴포넌트로 격리하되, 페이지 셸(Top Bar, 라우팅)은 서버 유지 |
| 실시간 동기화 (Realtime 구독, Optimistic UI) | 클라이언트 | Supabase Realtime 구독 훅을 사용하는 컴포넌트만 `'use client'` |

**원칙**: `'use client'` 경계는 가능한 한 **트리의 leaf(말단)**에 둡니다. 페이지 전체를 클라이언트화하지 말고, 상호작용이 필요한 최소 컴포넌트만 분리하여 서버 렌더링 이점(초기 로드, SEO, 번들 크기)을 유지합니다.

### 4.3 컴포넌트 디렉토리 구조

```
src/frontend/
├── components/
│   ├── ui/              ← 디자인가이드 §6 토큰 기반 공용 컴포넌트 (Button, Card, Modal, Input, Badge...)
│   ├── calendar/        ← 캘린더 전용 (CalendarGrid, CalendarCell, MemberFilterChip...)
│   ├── editor/          ← 캔버스 에디터 전용 (Canvas, StickerPalette, MapPreview...)
│   └── layout/          ← BottomTab, TopBar, Sidebar 등 글로벌 레이아웃
```

> `components/ui/`는 디자인가이드 §6 컴포넌트 목록(Button/Input/Card/Modal/Toast/Avatar 등)과 1:1 대응시켜 명명합니다. 프로토타입에서 새로운 시각 패턴이 발견되면, 먼저 §6 목록에 매핑 가능한지 확인 후 신규 컴포넌트 추가 여부를 결정합니다.
